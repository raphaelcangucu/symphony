# Internationalization (i18n) — Design

- **Date:** 2026-06-16
- **Status:** Accepted
- **Author:** Symphony agent + raphaelcangucu
- **Related:** `docs/superpowers/specs/2026-06-05-agent-preference-and-claude-native-design.md` (settings store pattern)

## Problem

Symphony has **no i18n infrastructure** today. User-facing strings are hardcoded
inline in two layers:

| Layer | Approx. scope | Language mix |
|-------|---------------|--------------|
| Tracker (`tracker/src/`) | ~500–800 strings in ~180 non-test files | Mostly English |
| Backend (`elixir/lib/`) | ~200–350 strings in ~25 modules | Mostly English |

A **Portuguese cluster** was added ad hoc for the return-to-agent / evidence
workflow and a few backend paths (assistant greetings, one push notification).
The result is an inconsistent UX: the same feature surfaces English and
Portuguese strings side by side.

Examples of hardcoded Portuguese in production code:

| String | Location |
|--------|----------|
| `Completar evidências` / VALIDATE handoff instructions | `tracker/src/lib/returnToAgent.ts` |
| `Nenhuma evidência registrada no tracker.` | `tracker/src/lib/evidenceStatus.ts` |
| `Retomar validação` / `Devolver ao agente` | `tracker/src/components/issues/issue-detail/ReturnToAgentPanel.tsx` |
| `Controles avançados` | `tracker/src/components/issues/issue-detail/AgentTab.tsx` |
| `Tarefa associada a você` | `elixir/lib/symphony_elixir/push_notifications/dispatcher.ex` |
| Conversational assistant fallbacks | `elixir/lib/symphony_elixir/assistant/session_manager.ex` |

**Out of scope for app i18n:** workflow status names like `Revisão de pares` or
`Em andamento` come from per-project `workflow_markdown` YAML (e.g.
`gamba-project.yaml`). They are project configuration data, not application
locale strings.

## Goals

- Introduce a proper i18n stack for **both** the React tracker and the Elixir
  backend.
- Support **`en`** and **`pt-BR`** as first-class locales.
- Default to **browser language detection** with fallback to **`en`**.
- Persist the operator's language preference in the existing **Settings** store
  (`/settings` page).
- Migrate the existing Portuguese cluster and high-visibility English strings
  incrementally — no big-bang rewrite.

## Non-goals

- Translating workflow status names stored in project YAML.
- More than two locales in v1 (no `es`, `fr`, etc.).
- Per-user locale when Symphony adds multi-operator auth (YAGNI — instance-level
  setting is sufficient today).
- Translating agent-generated content (Codex/Claude output, issue titles, PR
  bodies).

## Locale resolution

### Settings model

New settings group **`ui`** registered in `SymphonyElixir.Settings`:

```elixir
# SymphonyElixir.Settings.Ui
%{"locale" => "auto"}   # default
# cast: "auto" | "en" | "pt-BR"
```

Exposed via existing API:

- `GET /api/tracker/v1/settings` → includes `ui: { locale: "auto" }`
- `PUT /api/tracker/v1/settings/ui` → `{ "locale": "pt-BR" }`

### Client resolution (tracker)

Priority order when the app boots:

1. Fetch `settings.ui.locale` from the API.
2. If `"auto"` → detect from `navigator.language`:
   - prefix `pt` → `pt-BR`
   - otherwise → `en`
3. If explicit `"en"` or `"pt-BR"` → use as-is.
4. Final fallback → `en`.

The resolved locale initializes `react-i18next` before the first render of
user-facing UI (wrap app in `I18nProvider` inside `RequireToken` so settings are
available).

### Server resolution (Elixir)

| Context | Locale source |
|---------|---------------|
| Request-scoped (API errors, assistant channel replies, tool messages) | `X-Symphony-Locale` header sent by the tracker with the **resolved** client locale (`en` or `pt-BR`). Plug sets Gettext locale per request. Fallback: `en`. |
| Async / push notifications | Instance setting `ui.locale`. When `"auto"`, server uses **`en`** (no browser context at delivery time). When explicit, use that locale. |

This means push notifications and assistant greetings become Portuguese only
after the operator explicitly selects **Português (Brasil)** in Settings — not
when `"auto"` happens to detect PT in the browser. This is intentional and
documented in the Settings UI.

## Tech stack

### Tracker (React + Vite)

- **`i18next`** + **`react-i18next`**
- Locale files: `tracker/locales/en/*.json`, `tracker/locales/pt-BR/*.json`
- Lazy-load locale bundles on locale change.
- TypeScript: optional key typing via a thin wrapper or generated types (YAGNI
  for v1 — plain string keys are fine).

### Backend (Elixir + Phoenix)

- **`gettext`** (~> 0.26) added to `mix.exs`
- `SymphonyElixirWeb.Gettext` module
- Catalogs: `elixir/priv/gettext/en/LC_MESSAGES/*.po`,
  `elixir/priv/gettext/pt_BR/LC_MESSAGES/*.po`
- `SymphonyElixirWeb.Plugs.SetLocale` reads `X-Symphony-Locale` and calls
  `Gettext.put_locale/2`

### Cross-stack alignment

Backend API errors expose a stable `error.code` (already present in
`TrackerErrors`). Frontend maps `errors.api.<code>` keys so messages can be
translated client-side even when the server returns English `message` fields
during migration.

## Settings UI

New card on `/settings` — **Language**:

| Option | Value stored | Behavior |
|--------|--------------|----------|
| Auto | `"auto"` | Browser detection; push/async uses English |
| English | `"en"` | Force English everywhere |
| Português (Brasil) | `"pt-BR"` | Force Portuguese everywhere |

Card copy explains the push/async caveat for Auto. Saves via
`updateUiSettings({ locale })` mirroring `updateAgentSettings`.

Card strings themselves use i18n once the provider is wired (chicken-and-egg:
bootstrap with English keys for the Language card only, or render it after i18n
init — prefer init-before-render).

log text, lower user impact.

## Migration phases

### Phase 1 — Infrastructure + Portuguese cluster (this plan)

**Backend:**

- Add `gettext` dep, `SymphonyElixirWeb.Gettext`, `SetLocale` plug
- Add `Settings.Ui` group with `locale` default `"auto"`
- Migrate: `TrackerErrors`, `push_notifications/dispatcher.ex` (all kinds),
  `assistant/session_manager.ex`, `issue_dispatch.ex` response messages

**Tracker:**

- Add `i18next` / `react-i18next`, `I18nProvider`, locale detection helper
- Add `LanguageCard` + `updateUiSettings` service
- Send `X-Symphony-Locale` on all HTTP requests (axios interceptor)
- Migrate Portuguese cluster:
  - `returnToAgent.ts`
  - `evidenceStatus.ts`
  - `ReturnToAgentPanel.tsx`
  - `AgentTab.tsx` (`Controles avançados`)
- Migrate Settings page shell strings as proof-of-concept for English keys

**Tests:**

- Elixir: `Settings.Ui` cast/defaults, `SetLocale` plug, Gettext smoke for one
  error + one push string per locale
- Tracker: locale detection unit tests, LanguageCard save flow, migrated
  component tests updated to use `i18n` test helper

### Phase 2 — High-traffic surfaces

Issue drawer, agent control composer, preview tab, push notifications card,
orchestration card, project wizard, comments tab.

### Phase 3 — Remainder

Assistant panels, observability, backup, event humanizer, remaining toasts.

Each phase is independently shippable. Phase 1 must leave the app fully
functional in both locales for all migrated strings.

## Error handling

- Unknown locale in settings → cast fails → fall back to default `"auto"`.
- Missing translation key → i18next returns the key string in dev; log warning.
  Production: return key (same as dev for v1 — no silent English fallback that
  hides missing keys).
- Settings fetch fails on boot → use browser detection only (same as `"auto"`);
  retry on next navigation to Settings.

## Testing strategy

- **Unit:** `detectLocale()` with mocked `navigator.language`; `Settings.Ui`
  cast validation; Gettext `dgettext` returns correct string per locale.
- **Component:** wrap tests with `I18nProvider` + fixed locale; update
  Portuguese assertions to use `t()` keys or render with `pt-BR` bundle loaded.
- **Integration:** PUT settings/ui persists locale; subsequent GET reflects it;
  API error response respects `X-Symphony-Locale: pt-BR`.

## Acceptance criteria (Phase 1)

- [ ] Settings page shows Language card with Auto / English / Português (Brasil).
- [ ] Selecting a locale persists across page reload (via settings API).
- [ ] `"auto"` + browser `pt-BR` renders migrated tracker strings in Portuguese.
- [ ] `"auto"` + browser `en` renders migrated tracker strings in English.
- [ ] Explicit `"pt-BR"` makes push notification for issue assign Portuguese.
- [ ] Explicit `"en"` keeps push notifications in English.
- [ ] No hardcoded Portuguese remains in Phase 1 migrated files.
- [ ] `make all` and `cd tracker && npm test` pass.

## Open decisions (resolved)

| Question | Decision |
|----------|----------|
| Default locale strategy | Browser auto-detect with `en` fallback |
| Where to persist preference | Instance settings (`ui.locale`) |
| Push when locale is `"auto"` | English (documented in UI) |
| Supported locales v1 | `en`, `pt-BR` only |
| i18n libraries | Gettext (Elixir), react-i18next (tracker) |
